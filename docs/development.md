## Working copy location

Keep the checkout on the WSL ext4 filesystem (`~/projects/python/loan-simulator`) rather than
under `/mnt/c`. WSL reaches Windows drives through a file-sharing protocol that makes every file
open a round trip to the Windows side, and the virtualenv installs, `npm ci` and the test runs
open thousands of files.

## Frontend

`deploy.sh` serves the built page from the agent, at http://localhost:8101. For work on the
page, `npm run dev` in `frontend/` serves it with hot reload and proxies `/api` to the agent on
port 8101, so the stack must be up. Open the page as `localhost`, the origin Google sign-in is
registered for.

## Configuration

`./scripts/init-env.sh` creates the gitignored `secrets.sh`, `params.sh` and `aws-config.sh`
under `scripts/lib/` from [secrets.example.sh](../scripts/lib/secrets.example.sh),
[params.example.sh](../scripts/lib/params.example.sh) and
[aws-config.example.sh](../scripts/lib/aws-config.example.sh), keeping a file that already
exists; each setting's comment says what it holds and whether it is required. `deploy.sh` runs
it first on every run, and stops with a list of every setting it needs that is still blank.

- `secrets.sh` — the engine's bearer token and the database password, both generated by
  `init-env.sh`, the database URL built from them, and the model provider's API key.
- `params.sh` — this deployment's own settings that are no secret: `LLM_MODEL`,
  `GOOGLE_CLIENT_ID` ([Sign-in](sign-in.md) sets up the Google client), the per-person
  message limits, the retry model with the people allowed it (`LLM_RETRY_MODEL`,
  `LLM_RETRY_EMAILS`) and the license contact.
- `aws-config.sh` — the access key pair and region of the AWS account `deploy.sh --ec2`
  deploys to; a machine that deploys only locally leaves it unfilled.

Every other setting is committed in [stack-params.sh](../scripts/lib/stack-params.sh): the
ports, the database name and the addresses built from them. The agent refuses to start while
`LLM_MODEL`, `GOOGLE_CLIENT_ID` or `LLM_API_KEY` is blank. An edit to any of the three files
takes a `deploy.sh` run.

The engine's keys are `ENGINE_`-prefixed, the agent's are not. Compose hands each container only
the keys it reads, listed once per service in `docker-compose.yml`, so the engine never receives
the agent's model key or database password. A missing or malformed required setting stops
startup, and a blank value counts as missing. Each key is explained once, in `stack-params.sh`
or in the `.example.sh` beside a gitignored file; `mcp-server/tests/test_settings_files.py` and
`backend/tests/test_settings_files.py` fail when the files and the settings differ, each owning
its service's keys, and each service's `test_compose.py` fails when its container receives a key
it does not read. `ENGINE_BEARER_TOKEN` is defined once and read by both services.

A script that loads a settings file first stops if git would track it, or a tracked file holds
one of its secrets or email addresses, the license contact of `params.sh` excepted. It also
sets `core.hooksPath` to `.githooks`, whose `pre-commit` hook makes the same check on every
commit's staged changes.

The scripts export the three files into their shell before calling Compose, so a bare
`docker compose` call has no settings. The files hold the host forms of `DATABASE_URL` and
`ENGINE_URL`; Compose overrides both with the in-network addresses (`db:<DB_PORT>`,
`engine:<ENGINE_PORT>`). Host commands (pytest, uvicorn) run from the repo root, because the
agent reads the settings files by their path from the working directory.

## Backend tests

[`test.sh`](../scripts/test.sh) is the whole quality gate. It runs every target by default, or
the ones named: `engine` and `backend` each run the scripts' syntax check, ruff lint and format
check, mypy, the import-linter layer contracts and pytest; `frontend` runs oxlint, Vitest, the
TypeScript check and the Vite build. It needs Python 3.12+ for the engine and the backend, and
creates a separate `.venv` for each, since the engine uses MCP SDK 2.x while the agent's
`langchain-mcp-adapters` requires `mcp<2`; Node.js 22 for the page; and Docker, because the
backend's database tests start Postgres through Testcontainers. The GitHub Actions workflow runs
each target. [Testing](testing.md) states what each layer proves.

Each project's `tests/test_requirements_lock.py` fails until its lock matches its
`pyproject.toml` and the image; `tools/lock.sh` brings it back in line.

## Deployment scripts (`scripts/`)

Docker runs the stack; `deploy.sh` and `docker-helper.sh` stop when it is not reachable.

- [`deploy.sh`](../scripts/deploy.sh) — builds the images, starts Postgres (with its schema
  migration), the engine and the agent in Docker, and returns once the engine and the agent
  answer. Then open http://localhost:8101, sign in with a Google account,
  and start a check.
- `deploy.sh --ec2` — deploys to one EC2 instance in the account of `aws-config.sh`, and needs
  the AWS CLI, `ssh` and `curl`. It creates or updates the CloudFormation stack of
  [`template-ec2.yaml`](../scripts/template-ec2.yaml), builds the images here for ARM, loads them
  into the instance's Docker daemon over SSH and starts the stack there, and prints the
  CloudFront address to open and to register with Google
  ([Sign-in](sign-in.md#setting-up-google)). [The EC2 stack](#the-ec2-stack) covers what it
  deploys.
- `deploy.sh --ec2 --preview` — runs the working tree beside production on the same instance;
  [The preview on EC2](#the-preview-on-ec2) covers it, from the first deploy to its removal.
- [`docker-helper.sh`](../scripts/docker-helper.sh) — `--stop [--volumes]`, `--logs [-e]` or
  `--ps` for the stack; `--volumes` also removes the stored market data and the database. With
  `--ec2` as its first argument it acts on the instance, and `--ec2 --delete-stack` deletes
  the EC2 stack.
- [`test.sh`](../scripts/test.sh) — the quality gate, above.
- [`init-env.sh`](../scripts/init-env.sh) — creates the settings files, above; `--force`
  replaces existing ones, hand-filled keys included.
- `tools/` — hands-on tools: [`sql-helper.sh`](../scripts/tools/sql-helper.sh) (psql on the
  stack's database: a shell, `-c`, a SQL file, row counts and rows of every table,
  `--backup <file>` and `--restore <file>` of the whole database, and `--people` with
  `--reset <account-id>` or `--reset-all`, which delete a person's records so their next
  sign-in is a first visit, and `--clone <from> <to>`, which copies one account's checks to
  another with no records; `--ec2` first acts on the instance, `--ec2 --preview` on the
  preview, and `--ec2 --preview --copy-live` copies production's database into it; `--copy-live`
  alone copies it into this machine's database and migrates it there) and
  [`lock.sh`](../scripts/tools/lock.sh) (recompiles `mcp-server/requirements.txt` and
  `backend/requirements.txt` inside each Dockerfile's Python image; run it after editing a
  dependency list). [`tools/README.md`](../scripts/tools/README.md) lists them.

`scripts/common.sh` holds what the scripts share: the repo paths, the help printer, the loader
of the settings files, Compose access, and the virtualenv setup for the engine and the agent.
`lib/settings-guard.sh` keeps the gitignored files' values out of git, and `lib/ec2.sh` holds
the EC2 target: the stack's deploy, the SSH connection with an EC2 Instance Connect key, and
Compose pointed at the instance's Docker daemon. `template-ec2.yaml`, `lib/ec2.sh`,
`lib/settings-guard.sh` and `.githooks/pre-commit` are the same files in every Docker Compose
repo.

`docker-helper.sh --ec2 --delete-stack` deletes the EC2 stack after asking for its name; it fails
while a guest stack runs on the instance. The instance's disk stays in the account, since it
holds the databases; the command prints its volume id and the command that deletes it.

The IAM user of `aws-config.sh` needs to create and delete the stack's resources
(CloudFormation, EC2 instances, addresses and security groups, CloudFront distributions), to
read the public SSM parameter that names the Amazon Linux image, and
`ec2-instance-connect:SendSSHPublicKey` for the SSH connection. No IAM user has these by
default; an administrator has them all.

## The EC2 stack

`./scripts/deploy.sh --ec2` runs the same Compose stack on one EC2 instance
([ADR 0009](adr/0009-ec2-instance-behind-cloudfront.md)). A CloudFormation stack,
`scripts/template-ec2.yaml`, holds the instance (ARM, with only the Docker engine), its
fixed address, a security group and a CloudFront distribution, whose `https` address is the only
way in: the security group admits the agent's port from CloudFront's servers alone, and port 22
from the deployer's address. TLS ends at CloudFront, and the hop to the instance is plain HTTP.
`docker-compose.ec2.yml` holds what differs on the instance: images built for ARM, the agent
published on the instance's address, and services that start again with the instance. Compose
runs on the deployer's machine against the instance's Docker daemon. The settings files stay on
that machine, and no secret store is involved: each container's own settings, secrets included,
reach the instance as part of its configuration, which Docker keeps on the instance's encrypted
disk. That disk holds the database and outlives the instance.

The git branch selects the stack: `main` deploys `loan-simulator`, any other branch
`loan-simulator-fb`; an exported `STACK_NAME` wins. The stack is a host, with an instance of its
own, while `EC2_HOST_STACK` of `params.sh` is blank; set to another Docker Compose repo's host
stack, it deploys onto that instance as a guest, with its own port and CloudFront distribution
([ADR 0014](adr/0014-any-docker-repo-can-host-the-instance.md)); the host goes first. The `EC2`
block of `stack-params.sh` names the stack, its port and the instance type a host starts,
t4g.small; a change of the type stops and starts the same instance, which keeps its disk and its
address. Every deploy, host or guest, also makes sure the instance has a 1 GB swap file
(`prepare_ec2_host` in `lib/ec2.sh`), so a burst beyond the instance's 2 GB of memory slows the
stacks instead of killing a container.

## The preview on EC2

The preview runs the working tree, committed or not, beside production on production's instance,
so a change is tried on the real host before production gets it
([ADR 0013](adr/0013-a-preview-runs-beside-production.md)). It is the guest stack
`loan-simulator-preview`: its own CloudFront address, its own Compose project and so its own
database, its own image names (`loan-engine-preview:ec2`, `loan-agent-preview:ec2`) and ports
(8110 to 8112), all selected by `DEPLOY_PREVIEW` in `stack-params.sh`, which `--ec2 --preview`
sets. Production's containers, images and database are not touched. It uses the same settings
files as production, so the same model key and Google client.

The account needs, once:

- **The host stack on the current template**, which publishes the instance's address and
  offers four empty security groups attached to the instance: slots that name no guest. A rule
  that admits CloudFront's servers counts as 55 of a group's 60, the size of AWS's list of their
  addresses, so every stack's rule needs a group of its own. A guest's deploy claims a free slot
  (`ec2_guest_slot` in `lib/ec2.sh`), keeps it on later deploys, and frees it when its stack is
  deleted; with every slot held it stops and names the stacks holding them. A host stack
  deployed before the slots existed is brought up to date without a production deploy by a
  CloudFormation change set of `template-ec2.yaml` with every parameter at its previous value:
  it adds the four groups to the running instance, which keeps its id, disk and containers.

Then:

1. `./scripts/deploy.sh --ec2 --preview` creates the stack on its first run (the CloudFront
   distribution takes several minutes), builds and starts the preview, and prints its address.
2. Register that address with Google once, as an authorized JavaScript origin and, with a
   trailing `/`, an authorized redirect URI ([Sign-in](sign-in.md#setting-up-google)).
3. `./scripts/tools/sql-helper.sh --ec2 --preview --copy-live`, when the preview should hold
   production's data: after the database's name is typed, production's database is dumped
   (read only) straight into the preview's, the preview's schema is dropped first, and the
   preview's migration runs on the copy. The revisions it prints are production's and the one
   after the migration, so the run rehearses production's next upgrade; a failed migration
   leaves the copy at production's revision for inspection.

`docker-helper.sh --ec2 --preview` (`--logs`, `--ps`, `--stop`) and
`sql-helper.sh --ec2 --preview` act on the preview as they do on production.

`./scripts/docker-helper.sh --ec2 --preview --delete-stack` removes the preview, after its
stack's name is typed: its containers, database, market data and images on the instance, then its
stack, with its port rule and CloudFront distribution. Production is not touched. Its address is
then removed from the Google OAuth client by hand.

## Addresses

Each service has a port inside the Compose network, where the services reach each other by name,
and a port published on this machine's loopback interface only, where you reach it (the reason
is in the header of `docker-compose.yml`; `backend/tests/test_compose.py` checks it). As shipped
in `scripts/lib/stack-params.sh`:

| Service | On this machine | Inside the Compose network |
|---|---|---|
| Agent | `http://localhost:8101` (`AGENT_HOST_PORT`): the page at `/`, `/health`, `/ready`, `/api` | `agent:8000` (`AGENT_PORT`) |
| Engine | `http://localhost:8100/mcp` (`ENGINE_HOST_PORT`), for MCP Inspector | `engine:8020` (`ENGINE_PORT`) |
| Postgres | `127.0.0.1:8102` (`DB_HOST_PORT`), for an agent or a psql run on the host | `db:5432` (`DB_PORT`) |

A published port must be free on this machine; change it in `stack-params.sh` if it is not. A
new `AGENT_HOST_PORT` needs the same change in the Google client's authorized JavaScript origin
and redirect URI ([Sign-in](sign-in.md#setting-up-google)).

## Try the engine with MCP Inspector

```bash
npx @modelcontextprotocol/inspector
```

The command opens Inspector in the browser.

1. Add a server (or edit the HTTP one Inspector lists) with the transport **streamable-http** and
   the URL `http://localhost:<ENGINE_HOST_PORT>/mcp`.
2. In the server's **Settings**, under **Custom Headers**, add the header `Authorization` with
   the value `Bearer ` followed by `ENGINE_BEARER_TOKEN` from `secrets.sh`. Leave the OAuth
   settings empty: the engine takes this one fixed token.
3. Connect with the server's toggle, open **Tools** and pick `simulate_loan`. Its one argument,
   `loan`, takes the tracks of the loan; switch on **Edit as JSON** to paste them. For a loan of
   31,000 ₪ at prime + 2.9, 48 months, unlinked:

   ```json
   {"tracks": [{"principal": "31000", "term_months": 48, "rate_kind": "prime",
                "prime_spread": "2.9", "cpi_linked": false, "method": "spitzer"}]}
   ```

The result's structured content gives today's payment, the peak recurring payment and total,
the balloon due for a balloon track, the worst historical window (the past run of months as long
as the term whose rate and inflation moves give the highest payment) with its start and end
months, the range across all such windows, the schedule, and the data dates the figures rest on:
the Bank of Israel rate of today and the consumer price index of last month or the month before.
Its text content is a short summary of the same figures without the schedule, sized for a
language model's context.
